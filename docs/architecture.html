System design · event ticketing

Ticketmaster

Four HTTP services and three workers behind one gateway. The whole design turns on a single question: how do you sell ten thousand seats to a million people without ever selling one seat twice?

The shape of the problem

Ticketing is read-heavy with violently spiky writes. An event sits idle for weeks, then takes 100:1 oversubscription in seconds. Two properties fight each other under that load:

Availability wants caching. A seat map is read thousands of times per sale. Correctness forbids it. A cached seat map sells seats that are already gone.

The resolution runs through every diagram below: Redis holds intent, Postgres holds fact. Losing a hold is survivable — the seat reopens and nobody was charged. Losing a booking is not.

02 · The core invariant

Three independent guards against selling one seat twice

A single guard is a single point of failure, so the confirm path stacks three mechanisms that fail independently. Each one alone is sufficient; each covers a different way the others could be broken by a later change.

03 · Hold state

Three Redis structures, because the claim and the read want opposite things

The obvious design is one key per seat with a TTL. It makes the claim trivial and the seat map impossible: rendering a 50,000-seat event would be 50,000 round trips.

04 · Fairness under 100:1

Queue, admission, and why FIFO is the wrong answer

A million users, ten thousand seats. Nine hundred and ninety thousand people leave disappointed no matter what the code does, so "fairness" is a policy choice, not a property you can implement your way into.

Pure FIFO rewards fibre and proximity. It selects for the fastest network and for bots that pre-warm connections, while looking fair. So the queue registers everyone first, then draws an order from a seed that does not exist until the sale opens.

05 · Money

Three transactions, and why one would be wrong

The tempting shape is a single transaction wrapping the booking and the charge. It is wrong in a way that only appears on a crash — and it fails in the worst possible direction.

The Redis-down case was a genuine bug before the drill found it. node-redis queues commands while disconnected by default, so every reserve hung indefinitely rather than failing — turning a cache outage into a total outage. disableOfflineQueue fixes it. Fail fast, not queue quietly.

Scope honesty

Single-node Postgres, Redis, and Elasticsearch — no replication, no failover. Multi-instance tests run several local processes, not machines or network partitions.

All services share one database, and both Event and Booking read tickets. That is a split-by-process, not real service isolation: the data coupling remains and network hops were added. Real boundaries mean a database per service, which turns the booking↔ticket write into a distributed transaction. A deliberate trade, and the honest answer to "who owns the tickets table?" is "shared."

CDC is a transactional-outbox poller, not log-based replication. Debezium plus Kafka is the production answer — describable here, not demonstrated.

Per-user caps and payment-instrument uniqueness are in scope. Nothing here stops an attacker holding ten thousand verified identities; that is identity verification, and it is the part the real Ticketmaster still loses.
